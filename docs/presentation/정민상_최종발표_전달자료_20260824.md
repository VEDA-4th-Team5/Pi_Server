## 2. Raspberry Pi 서버 전체 흐름

### 2.1 주차면 입차·출차

```text
Camera CH1/CH3 WiseAI IVA
  -> ONVIF CreatePullPointSubscription
  -> PullMessages 반복 수신
  -> VideoSourceToken + RuleName 매핑
  -> Intrusion/Exit 상태 변환
                                      ┐
                                      ├-> 하이브리드 점유 판정
STM32 Hall 센서                       │   -> SQLite 주차 세션 생성·갱신
  -> UART 또는 E22 LoRa               │   -> 증거 촬영 예약
  -> Frame Decode / Parser            │   -> Qt MQTT 상태·이벤트 발행
  -> Debounce 후 OCCUPIED/VACANT -----┘
```

입차는 카메라 IVA 또는 Hall 센서 중 하나가 유효한 점유를 확인하면 시작할 수 있다. 뒤이어 다른 센서가 같은 점유를 확인해도 새 세션을 만들지 않고 기존 세션의 확인 상태를 보강한다.

출차는 세션에서 실제로 점유를 확인했던 센서 상태를 고려한다. IVA만 확인한 세션은 IVA Exit 확인 절차를 사용하고, Hall만 확인한 세션은 Hall VACANT를 사용한다. 두 센서가 모두 확인한 세션은 다른 센서가 명백히 점유 상태인지를 확인하여 잘못된 조기 종료를 방지한다.

### 2.2 증거 이미지와 OCR

```text
점유 세션 생성
  -> OCCUPANCY_START 및 예약 시점 촬영
  -> Camera Snapshot API로 original/enhanced 이미지 수신
  -> Qt IVA Setup에서 저장한 최신 ROI 조회
  -> 주차면 영역 Crop
  -> Gemini 번호판 OCR
  -> IMAGE_LOG 및 PARKING_SESSION 반영
  -> Qt Evidence 화면에서 원본·개선본 조회
```

ROI가 없더라도 이미 커밋된 점유 상태를 반복 처리하지 않도록 상태 이벤트와 Crop/OCR 실패를 분리했다. ROI 미설정은 한 번 경고하고, 점유 트랜잭션 자체는 재시도 폭주를 일으키지 않게 처리한다.

### 2.3 CH2 입구 차량 인식

```text
CH2 Plate BestShot 수신
  -> camera_id + channel_id + object_id로 객체 묶음
  -> Plate 이미지 다운로드
  -> 전기차 아이콘 분석
  -> Gemini 번호판 OCR
  -> VEHICLE UPSERT
  -> ENTRANCE_RECOGNITION 결과 저장
  -> 주차 세션 OCR과 시간·번호 유사도로 연결
```

동일 ObjectId의 반복 BestShot은 객체 키로 억제하고, ObjectId가 달라도 이미지가 동일하면 pHash 유사도로 중복 OCR을 방지한다. 정상 판정 후 임시 이미지는 삭제하고 차량번호, `is_ev`, 신뢰도, 판정 결과는 DB에 남긴다. 실패 자료는 원인 분석을 위해 보존 기간을 적용한다.

### 2.4 화재 알림

```text
STM32 Flame 센서
  -> UART/LoRa 수신
  -> Pi 화재 상태 머신 OPEN/ACKNOWLEDGED/RESOLVED
  -> SQLite 상태·Outbox 저장
  -> MQTT로 Qt 경보 발행
  -> Telegram 운영자 메시지
  -> Qt ACK 명령 수신 및 상태 반영
```

## 3. 주요 구현 내용

### 3.1 CH1·CH3 ONVIF IVA 확장

- CH1: `vs-0`, `name1`~`name4`를 EV01~EV04에 매핑
- CH3: `vs-2`, `name5`~`name8`을 일반 주차면 P01~P04에 매핑
- 카메라 ONVIF Event Service에 WS-Security PasswordDigest로 인증
- `CreatePullPointSubscription` 후 `PullMessages`를 반복 호출
- XML에서 `VideoSourceToken`, `RuleName`, `Action`, `ObjectId`, 발생 시각 추출
- `Intrusion`과 `Exit`을 주차 점유 신호로 변환
- 연결 실패 시 재구독하고 서버 종료 시 구독 해제
- ONVIF 모드에서는 고정 MQTT IVA Publication을 점유 전이에 사용하지 않아 중복 입력 방지

발표에서 사용할 설명:

> CH1에서는 카메라의 원본 WiseAI 이벤트가 MQTT로 전달됐지만 CH3에서는 고정 Publication만 전달되어 Exit을 구분할 수 없었습니다. 카메라 Event Service를 직접 구독하는 ONVIF PullPoint 입력을 Pi 서버에 추가해 CH1과 CH3 모두 실제 Intrusion/Exit을 동일한 형식으로 처리했습니다.

### 3.2 Hall·IVA 하이브리드 점유 판정

- IVA와 Hall 중 하나만 정상이어도 입차를 감지하는 OR 구조
- 동일 차량에 두 입력이 연속 도착해도 활성 세션은 하나만 유지
- `hall_confirmed`, `iva_confirmed`, `hall_occupied`, `iva_occupied` 상태를 세션에 저장
- 센서 입력 순서가 달라도 동일한 상태 전이 명령을 멱등하게 처리
- 출차는 해당 세션에서 실제 점유를 확인한 센서를 기준으로 판정
- 재시작 후 ACTIVE 세션과 출차 확인 Deadline 복원

### 3.3 Camera Snapshot API와 Evidence

- 카메라에서 original/enhanced 이미지를 생성·다운로드
- 주차면과 카메라 채널 매핑에 따라 CH1 또는 CH3 이미지 요청
- Qt가 저장한 최신 ROI 좌표를 SQLite에서 복원
- `session_id`, `slot_id`, 촬영 사유, ROI revision을 IMAGE_LOG에 저장
- 점유 시작·예약 촬영·장기점유 증거를 단계별 디렉터리에 저장
- 조기 출차 시 임시 이미지와 예약 작업 정리
- 위반 세션의 증거 데이터는 보존

### 3.4 CH2 입구 BestShot

- 물리 CH2 RTSP 경로와 서버 채널 ID를 `ch02`로 통일
- Plate BestShot을 처리 대상으로 사용
- 차량 아이콘 판정이 완료된 뒤 Gemini OCR 실행
- 객체 키와 pHash를 이용한 중복 처리 억제
- OCR 성공 시 VEHICLE의 차량번호 및 이진 `is_ev` 값 저장
- 입구 OCR 결과를 이후 주차 세션 OCR과 정확·유사 번호판으로 연결
- 정상 처리 파일 자동 삭제, 실패 파일 제한 보존

### 3.5 HTTPS REST API와 인증

- cpp-httplib OpenSSL 서버 사용
- TLS 인증서와 개인키를 로컬 비공개 설정으로 관리
- Argon2id 비밀번호 Hash 저장
- 로그인 성공 시 Bearer Token 발급
- 원문 Token 대신 SHA-256 Digest만 DB 저장
- 인증 실패, 요청 제한, 잘못된 입력을 HTTP 상태 코드로 구분

### 3.6 Linux 문자 디바이스 연동

- `/dev/parking_alert` 문자 장치를 C++ 서버 Adapter와 연결
- 주차 위반 상태를 비트 마스크로 커널에 SET/CLEAR
- `poll`, blocking `read`, `ioctl`을 이용해 사용자 공간과 상태 전달
- 커널 6.1 환경에서 빌드 호환성 보완
- 서버 시작 전 모듈 자동 적재 및 장치 준비 절차 구성
- 장치 오류가 MQTT·DB의 이미 커밋된 상태를 되돌리지 않도록 부수 효과로 분리

## 4. AI HTTPS 요청·응답 구조

### 4.1 사용 API

```text
POST https://generativelanguage.googleapis.com/v1beta/models/{MODEL}:generateContent
Content-Type: application/json
x-goog-api-key: <환경변수에서 로드, 출력·커밋 금지>
```

서버 구현은 C++ `libcurl`을 사용한다. 연결 제한 시간은 5초, 전체 요청 제한 시간은 30초로 설정되어 있다.

### 4.2 요청 구조

```json
{
  "contents": [
    {
      "role": "user",
      "parts": [
        {
          "text": "대한민국 자동차 번호판을 판독하고 추측하지 말라는 OCR 지시문"
        },
        {
          "inline_data": {
            "mime_type": "image/jpeg",
            "data": "<Base64로 변환한 번호판 이미지>"
          }
        }
      ]
    }
  ],
  "generationConfig": {
    "temperature": 0,
    "responseMimeType": "application/json",
    "responseSchema": {
      "type": "OBJECT",
      "properties": {
        "readable": {"type": "BOOLEAN"},
        "plate_number": {"type": "STRING"},
        "confidence": {"type": "NUMBER"}
      },
      "required": ["readable", "plate_number", "confidence"]
    }
  }
}
```

- JPEG와 PNG만 허용한다.
- 한 이미지의 최대 크기는 15 MiB다.
- 원본과 개선본이 모두 있으면 한 요청에 함께 넣어 비교한다.
- API Key는 URL이나 JSON 본문이 아니라 HTTP Header로 전달한다.

### 4.3 응답 처리

Gemini 응답의 `candidates[0].content.parts[0].text` 안에 있는 JSON 문자열을 다시 파싱한다.

```json
{
  "readable": true,
  "plate_number": "12가****",
  "confidence": 0.93
}
```

처리 규칙:

- `readable=false`이거나 국내 번호판 형식이 아니면 미인식으로 분리
- 번호판의 공백과 하이픈을 정규화
- HTTP 401/403은 인증 오류, 429는 요청 제한, 5xx는 서버 오류로 분류
- 재시도 가능한 오류는 최대 3회 제한 Backoff 적용
- 대체 모델은 기본 모델이 404로 제공되지 않을 때만 사용
- OCR 성공 결과를 VEHICLE, PARKING_SESSION, IMAGE_LOG 또는 ENTRANCE_RECOGNITION에 반영

### 4.4 개인정보 설명

연속 RTSP 영상 전체를 클라우드에 전송하지는 않는다. 번호판 판독이 필요한 시점에 선택한 Crop 또는 BestShot 이미지만 Gemini HTTPS API로 전송한다. 따라서 발표에서는 “완전 로컬 AI”가 아니라 “이벤트 기반 선택 이미지 HTTPS OCR”이라고 설명해야 정확하다.

### 6.2 MQTT

Pi가 Qt로 발행:

```text
parking/v1/events/{slot_id}  QoS 1, retain=false
```


## 11. 문제 분석과 해결 사례

### 사례 1. Hall과 IVA 동시 입력의 중복 세션 위험

- 현상: 동일 차량에 대해 카메라 IVA와 Hall 센서 신호가 가까운 시각에 도착
- 위험: 두 입력 경로가 각각 새로운 주차 세션을 생성할 수 있음
- 분석: 입력 로그, 점유 명령 ID, SQLite 세션 상태를 비교
- 해결: 점유 상태 전이를 단일 DB 트랜잭션 경로로 통합하고 센서별 확인 상태만 기존 세션에 추가
- 검증: IVA→Hall, Hall→IVA, 동시 도착 순서를 바꿔 회귀 시험

### 사례 2. CH3 WiseAI Exit을 MQTT Publication으로 구분하지 못한 문제

- 현상: CH1은 원본 WiseAI Intrusion/Exit이 왔지만 CH3은 고정 `INTRUSION` Payload만 반복 수신
- 분석: Mosquitto의 원본 WiseAI Topic과 고정 Publication Topic을 동시에 관찰
- 원인: Pi 필터 문제가 아니라 카메라가 CH3 원본 WiseAI MQTT 이벤트를 Broker에 발행하지 않는 구성
- 해결: 카메라 ONVIF Event Service를 직접 구독해 실제 Action과 ObjectId를 수신
- 결과: CH1 `name1~4`와 CH3 `name5~8`을 같은 코드 경로에서 처리

### 사례 3. ROI 미설정으로 동일 후속 작업이 반복된 문제

- 현상: `Qt parking event ROI is missing` 이후 동일 점유 로그와 촬영 예약이 반복
- 원인: DB에 이미 커밋된 점유 효과를 ROI 누락 때문에 전체 실패로 반환
- 해결: 상태 이벤트 발행과 Crop/OCR 가능 여부를 분리하고 ROI 누락은 한 번의 경고로 제한
- 결과: 주차 상태는 유지하면서 잘못된 무한 재시도를 방지

### 사례 4. 반복 BestShot으로 OCR 비용이 증가하는 문제

- 현상: 같은 차량이 입구에 머물면 동일하거나 유사한 Plate 이미지가 반복 도착
- 해결: 객체 키 TTL과 pHash 유사도 비교를 함께 사용
- 결과: ObjectId가 같을 때와 달라졌을 때 모두 중복 OCR을 억제

### 사례 5. Qt와 Pi의 HTTPS 인증서 신뢰 문제

- 현상: 서버는 TLS로 열렸지만 Windows Qt Client가 자체 서명 인증서를 신뢰하지 못함
- 해결: 내부 CA·서버 인증서 구조를 구분하고 Qt의 인증서 처리 방식과 서버 OpenSSL 설정을 정합
- 검증: `/api/v1/health` HTTPS 200 응답 확인

## 13. 자체 평가

### 잘한 점

카메라, Raspberry Pi, STM32, Qt 중 한 부분만 정상인지 확인하지 않고 실제 이벤트가 입력되어 DB 상태, 이미지, OCR, MQTT 화면까지 이어지는 전체 경로를 통합했다. 특히 센서 입력 순서와 중복, 네트워크 오류, 서버 재시작처럼 정상 시연 외의 조건을 상태 전이와 SQLite 기록으로 다룬 점이 가장 큰 성과다.

### 어려웠던 점

같은 “차량 감지”라도 카메라 IVA, 고정 MQTT Publication, Hall 센서가 서로 다른 시간과 형식으로 전달됐다. CH3처럼 카메라 웹 화면에는 이벤트가 보이지만 Broker에는 원본 이벤트가 오지 않는 경우도 있어 Pi 코드, MQTT 설정, 카메라 내부 이벤트 중 어느 구간인지 분리하는 작업이 어려웠다.

### 해결 과정에서 배운 점

복합 시스템에서는 로그 한 줄만 보고 원인을 단정하면 안 된다. 원천 이벤트, 변환 이벤트, DB 트랜잭션, 외부 부수 효과를 구분하고 같은 시각의 데이터를 비교해야 원인 구간을 좁힐 수 있다. 수정 후에는 입력 순서와 오류 조건을 바꿔가며 같은 문제가 재발하지 않는지 확인해야 한다.

### 아쉬운 점과 개선 방향

- 최신 EVDA-238 바이너리로 전체 42개 테스트를 아직 일괄 완료하지 못함
- 최신 바이너리 재시작 후 CH2 입구 DB Migration과 실기기 End-to-End 재검증 필요
- P01~P04의 Qt ROI를 모두 저장하고 CH3 입차 Evidence 촬영 확인 필요
- Camera Snapshot API 409와 Gemini 429 발생 조건을 재시험해야 함
- 장시간 부하, 네트워크 단절·복구, 저장 공간 고갈 시험이 부족함
- CPU·메모리 수치를 최종 시연 조건에서 다시 측정해야 함

## 14. 발표자료에 바로 넣을 문장

### 역할

> Raspberry Pi C++ 서버에서 Hanwha Vision 카메라, STM32 Hall·Flame 센서, SQLite, Qt 관제 클라이언트를 연결하고 주차 상태 전이, 증거 촬영, OCR, 화재 알림을 통합했습니다.

### 핵심 성과

> Hall 센서와 카메라 IVA 중 하나만 정상이어도 입차를 감지하면서, 두 신호가 동시에 도착해도 하나의 주차 세션만 유지하는 하이브리드 점유 판정 구조를 구현했습니다.

### CH3 문제 해결

> CH3의 원본 WiseAI MQTT 이벤트가 전달되지 않는 문제를 원천 이벤트와 고정 Publication을 분리해 확인하고, ONVIF PullPoint 직접 구독을 추가해 CH1과 CH3의 Intrusion·Exit을 동일하게 처리했습니다.

### 검증

> 정상 경로뿐 아니라 중복 입력, CRC 오류, 분할 수신, Timeout, 센서 Sequence 역행, 네트워크 복구를 테스트 조건으로 정의하고 동일 조건으로 회귀 검증할 수 있게 구성했습니다.

### 정량 결과

> Raspberry Pi 실기기에서 서버 프로세스는 약 74 MiB의 RSS와 평균 약 15.5%의 CPU를 사용했으며, 증거 이미지 94개의 평균 크기는 약 49 KiB였습니다.

### 느낀 점

> 복합 시스템에서는 기능 구현만큼 원천 입력, 상태 전이, DB 기록, 외부 전송을 분리해 관찰하는 것이 중요하다는 것을 배웠습니다. 실패 조건을 재현하고 수정 후 같은 조건으로 검증하는 개발 습관을 갖게 됐습니다.
