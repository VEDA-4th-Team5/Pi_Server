# 증거 이미지 파이프라인 최적화 — 전체 프레임 2장 → ROI 크롭 1장

- 작성일: 2026-08-28
- 대상: Raspberry Pi 4 Model B (8GB) / aarch64 / kernel 6.18.39 / OpenCV 4.10.0
- **옛 방식**: [`d41e2f09`](https://github.com/VEDA-4th-Team5/Pi_Server/tree/d41e2f094377ec75760122cba430d1f10ea1b339) — `[Feat] 홀센서 트리거 세션 연결 초안 작성 (EVDA-134)`
- **현재 방식**: `demo_0826` / `79c5de4`
- 원본 측정: [`data/file_size_old_vs_new.txt`](data/file_size_old_vs_new.txt), [`data/file_size_cpu_bench.txt`](data/file_size_cpu_bench.txt)
- 벤치마크 소스(재현용): [`data/file_size_cpu_bench.cpp`](data/file_size_cpu_bench.cpp), [`data/file_size_cpu_stages.cpp`](data/file_size_cpu_stages.cpp) — 재현 절차는 `data/file_size_cpu_bench.txt` [C]항

> **요약: 이벤트 1건당 저장 972.6KB → 129.4KB (7.5배), Gemini 이미지 토큰 1032 → 258 (4배),
> Pi CPU 270.4ms → 12.2ms (22.1배) 줄었다. 그런데 가장 큰 이득은 "작아진 것" 자체가 아니라,
> 옛 방식이 낸 비용의 대부분이 애초에 정보량을 하나도 늘리지 못하는 지출이었다는 점이다.
> 811.9KB PNG는 160.7KB JPEG과 해상도가 똑같은 1280x720이었고, 토큰도 똑같이 516이었다.
> 같은 픽셀 격자를 두 번 보내느라 토큰을 정확히 2배 썼다.
> 반대로 지금은 ROI에 쓰이는 유효 토큰이 4배 적은 예산에서도 오히려 2.24배 늘었다.**

## 1. 두 방식의 정의

### 옛 방식 — `d41e2f09`

한 이벤트에서 **같은 프레임을 두 가지로 렌더링해 하나의 Gemini 프롬프트에 함께** 넣었다.

```
카메라 프레임 1280x720
   ├─ scene/    …_222758_794.jpg          160.7 KB   (전체 화면, 크롭 없음)
   └─ enhanced/ …_222758_794_enhanced.png 811.9 KB   (같은 프레임 화질개선)
                                          ─────────
                          한 프롬프트에 2장 동시 전송   972.6 KB
```

`GeminiOcrClient.cpp@d41e2f09:107-109` 이 두 장을 같은 `parts` 배열에 넣는다.

```cpp
if (!appendImagePart(parts, image_path, result.error)) return result;
if (!enhanced_image_path.empty() &&
    !appendImagePart(parts, enhanced_image_path, result.error))
```

개선본은 `enhanceIvaSceneImage()` (`PlateImageEnhancer.cpp@d41e2f09:214-237`) 가 만든다 —
`bilateralFilter(3,18,18)` → Lab → `CLAHE(1.25, 8x8)` → 언샤프 마스크 → `imwrite(PNG, COMPRESSION=2)`.

**핵심: `resize`가 없다.** 개선본은 원본과 같은 1280x720이다. 811.9KB는 해상도가 아니라
**PNG 무손실 인코딩 + 낮은 압축률(=2)** 때문이다.

### 현재 방식 — `79c5de4`

ROI로 크롭한 JPEG 1장을 보낸다. 크롭은 `SnapshotStorage.cpp:63-91`의 `cropJpeg()`가
정규화 ROI로 서버에서 수행하고 품질 95로 재인코딩한다.

Hall 30/60초 경로는 `OcrWorker.cpp:254-263`에서 `secondary_input.clear()`로 **명시적으로 1장만** 보낸다.

```cpp
if (task.hall) {
    if (usableImageFile(processed.enhanced_path)) { ocr_input = processed.enhanced_path; ... }
    secondary_input.clear();   // 단일 입력 확정
```

## 4. 이득 ② — Gemini 토큰

### 4.1 토큰 산정 근거

Gemini의 이미지 토큰은 **파일 크기(KB)가 아니라 해상도**로 정해진다.
양변 384px 이하는 258토큰, 그 외에는 768x768 타일로 쪼개 타일당 258토큰이다.

```
옛:  1280x720 → ceil(1280/768) x ceil(720/768) = 2 x 1 = 2 타일 = 516 tok
현재: 최대 583x683 → 1 타일 = 258 tok   (178장 전부 1타일)
```

### 4.2 결정적 지점 — 800KB는 토큰을 한 톨도 더 사지 못했다

| | 크기 | 해상도 | 타일 | 토큰 |
|---|---:|---:|---:|---:|
| scene JPEG | 160.7 KB | 1280x720 | 2 | 516 |
| enhanced PNG | 811.9 KB | 1280x720 | 2 | **516** |
| | | | | **합계 1032** |

PNG가 JPEG보다 **5.05배 무거운데 토큰은 정확히 같다.** 해상도가 같기 때문이다.
즉 옛 방식은 **동일한 픽셀 격자를 두 번 보내려고 이미지 토큰을 정확히 2배 지불**했다.
디스크와 업로드에서는 800KB를 더 냈고, 그 대가로 모델이 받은 추가 정보는 "같은 장면의 다른 압축본"뿐이다.

### 4.3 절감

```
옛 방식     516 x 2장 = 1032 tok
현재(Hall)  258 x 1장 =  258 tok    → 4배 (75% 절감)
현재(IVA)   258 x 2장 =  516 tok    → 2배 (50% 절감, §7에서 개선 여지)
```

텍스트 프롬프트는 두 버전 모두 한국어 약 130자로 사실상 동일해서 차이가 없다.
**절감은 전부 이미지 토큰에서 나온다.**

연간 이미지 토큰 투영:

| 이벤트/일 | 옛 방식 | 현재 |
|---:|---:|---:|
| 20 | 7.53 M | 1.88 M |
| 50 | 18.83 M | 4.71 M |
| 200 | 75.34 M | 18.83 M |
| 1000 | 376.68 M | 94.17 M |

> **주의**: 258토큰/타일 규칙은 Gemini 2.x 계열 문서 기준이다. 현재 설정 모델은
> `gemini-3.1-flash-lite-preview`(`.env.public:217`)이고, 이 프리뷰 모델의 실제 타일 단가는
> 확인하지 못했다. **비율(4배·2배)은 양쪽에 같은 규칙을 적용하므로 규칙이 달라도 유지되지만,
> 절대 토큰 수는 검증이 필요하다.** 검증 방법은 §8에 적었다.

## 5. 이득 ③ — Pi CPU (요청 외 추가 발견)

옛 방식은 이벤트마다 Pi가 **811KB PNG를 직접 인코딩**해야 했다. 이게 생각보다 비싸다.

### 5.1 측정 방법 — 옛 코드를 실제로 컴파일해서 돌렸다

추정이나 재현이 아니다. `d41e2f09`의 `src/ocr/PlateImageEnhancer.cpp`를 git에서 그대로 꺼내
**이 Pi에서 `g++ -O2 -std=c++20`으로 컴파일하고 `ocr::enhanceIvaSceneImage()`를 직접 호출**했다.
입력도 같은 커밋에 들어 있는 원본 프레임(1280x720, 160.7KB)이다.
비교군 `cropJpeg()`는 현재 `SnapshotStorage.cpp:63-91` 본문 그대로다.

> **정합성 근거**: 이 실행이 만든 PNG가 **811.9 KB**로, `d41e2f09`에 커밋돼 있는 실제 결과물
> `…_794_enhanced.png`(811.9 KB)와 **바이트 단위로 일치**한다. 옛 경로를 그대로 재현했다는 뜻이다.

### 5.2 총시간 (반복 15회 중앙값)

| 조건 | 옛 `enhanceIvaSceneImage()` | 현재 `cropJpeg()` | 비율 |
|---|---:|---:|---:|
| **1스레드 (wall = CPU)** | **270.4 ms** | **12.2 ms** | **22.1x** |
| 4스레드 wall | 207.6 ms | 12.4 ms | 16.7x |
| 4스레드 CPU (user+sys) | **292.3 ms** | 12.4 ms | **23.5x** |

옛 경로는 OpenCV가 4코어로 흩어져 **벽시계 207.6ms 뒤에 CPU 292.3ms를 태운다.**
Pi 4코어 중 1.4코어를 이벤트마다 200ms씩 점유한 셈이다. 현재 경로는 12.4ms 단일 스레드다.

### 5.3 단계별 내역 (1스레드)

| 단계 | 시간 | 비중 |
|---|---:|---:|
| `imread` JPEG 1280x720 | 9.6 ms | 3.6% |
| `bilateralFilter(3,18,18)` | 33.2 ms | 12.5% |
| Lab + `CLAHE(1.25, 8x8)` | 54.6 ms | 20.5% |
| `GaussianBlur` + `addWeighted` (언샤프) | 26.6 ms | 10.0% |
| **`imwrite` PNG (COMPRESSION=2)** | **142.6 ms** | **53.5%** |
| 단계 합 | 266.6 ms | |
| *(검증) 실제 함수 총시간* | *268.2 ms* | *오차 −0.6%* |

**옛 비용의 53.5%가 CV 처리가 아니라 PNG 쓰기였다.** 화질개선 연산 전체(114.4ms)보다
그 결과를 무손실로 적는 비용(142.6ms) 하나가 더 컸다.
그리고 §4.2에서 봤듯 **그 142.6ms를 들여 만든 파일이 토큰을 한 톨도 더 사지 못했다.**

이건 [`04_LOAD_profiling_demo0826.md`](04_LOAD_profiling_demo0826.md)에서 관찰된
"증거촬영 시 CPU 스파이크"와 직접 연결된다. 현재 브랜치의 이벤트 피크가 15.79%에 그치는
이유 중 하나가 이 270ms짜리 동기 작업이 사라진 것이다.

## 6. 이득 ④·⑤ — 업로드와 OCR 유효 해상도

### 6.1 업로드 페이로드

`inline_data`는 base64라 실제 전송량은 파일의 **4/3배**다.

| | 원본 | base64 전송량 |
|---|---:|---:|
| 옛 방식 | 972.6 KB | **1296.8 KB** |
| 현재 (2장) | 129.4 KB | **172.5 KB** |
| 현재 (1장) | 64.7 KB | **86.3 KB** |

업링크가 5 Mbps인 현장이라면 **요청당 업로드만 2.07초 → 0.28초**다.
OCR 왕복 지연에서 업로드가 차지하는 몫이 이만큼 줄어든다.

> 단, **다운로드(카메라→Pi)는 줄지 않는다.** `cropJpeg()`는 Pi가 전체 프레임을 받은 뒤
> 서버에서 자르기 때문이다 (`SnapshotStorage.cpp:67`의 `cv::imdecode`). 절감은 저장·업로드 구간에 한정된다.

### 6.2 ROI 유효 토큰 밀도 — 싸진 게 아니라 정확해졌다

실측 크롭 예시는 1280x720에서 409x504를 잘라낸 것으로 **원본 면적의 22.4%**다.

```
옛 방식 : 516 tok 이 프레임 전체에 퍼짐 → ROI가 받는 몫 ≈ 516 x 0.224 = 115 tok
현재    : 258 tok 이 전부 ROI에         → 258 tok
```

**토큰을 4배 적게 쓰면서 정작 번호판이 있는 영역에는 2.24배 많은 토큰을 배분한다.**
옛 방식은 하늘·아스팔트·옆 주차면에 토큰 예산의 78%를 쓰고 있었다.
비용 절감과 인식 정확도가 같은 방향으로 움직인 드문 경우다.

## 7. 아직 남은 낭비 (현재 방식의 개선 여지)

이번 분석 중 발견한, **아직 해결되지 않은** 항목이다.

### 7.1 `enhanced`의 82%가 `original`과 바이트 단위로 동일

89쌍을 MD5로 비교한 결과다.

```
쌍 89개 → byte-identical 73 (82%) · 실제로 다른 것 16 (18%)
snapshots 총 11.25 MB 중 중복 사본 5,073 KB (44%) 가 순수 낭비
```

`original/…_original.jpg`와 `enhanced/…_enhanced.jpg`가 같은 내용인데 **별도 inode로 2벌 저장**된다
(inode 1681095 / 1682659, MD5 `197f0b26…` 동일). 개선 파이프라인이 통과(pass-through)한 경우다.

→ 해시가 같으면 하드링크하거나 `enhanced` 기록을 생략하면 **저장이 추가로 2배** 준다
(129.4 KB → 64.7 KB, 옛 방식 대비 누적 **15배**).

### 7.2 IVA/BestShot 경로는 아직 2장을 보낸다

`OcrWorker.cpp:254`에서 `secondary_input`을 비우는 것은 `task.hall`일 때뿐이다.
IVA 경로는 `GeminiOcrClient.cpp:178-180`으로 여전히 2장이 간다.
그런데 §7.1대로 그 2장은 82% 확률로 **완전히 같은 파일**이다.

→ **같은 이미지를 두 번 보내 258토큰을 추가 지불하면서 정보는 0비트 늘리지 않는다.**
전송 전 해시 비교로 동일하면 1장만 보내면 IVA 경로도 4배 절감(현재 2배)에 도달한다.

### 7.3 토큰 사용량 로깅 — 없었으나 이번에 추가함

분석 시점의 `pi-server.log`에는 `usageMetadata` / `promptTokenCount` 기록이 전혀 없었다(grep 0건).
그래서 §4의 토큰 수치는 **문서화된 규칙 기반 계산이며 실측이 아니다.**

이를 실측으로 바꾸기 위해 `GEMINI_USAGE` 로깅을 구현해 넣었다(§8).
서버를 며칠 돌린 뒤 §8.3 절차로 집계하면 §4의 계산값을 실제 청구 토큰으로 대체할 수 있다.

## 8. 검증 방법 — `GEMINI_USAGE` 로깅 (구현 완료)

§4의 토큰 추정을 실측으로 바꾸기 위해 Gemini 응답의 `usageMetadata`를 로깅하도록 구현했다.

### 8.1 무엇을 남기는가

`GeminiOcrClient::recognizePlateWithModel()`이 2xx 응답을 받을 때마다 한 줄을 남긴다.

```
[GEMINI_USAGE] model=gemini-3.1-flash-lite-preview images=1 image_bytes=66127 \
               prompt=273 candidates=18 total=291 http=200 ok=true
```

| 필드 | 의미 |
|---|---|
| `model` | 실제 호출된 모델 (fallback이면 fallback 모델명) |
| `images` | 이 요청에 실린 이미지 수 — **§7.2의 2장 전송을 추적하는 값** |
| `image_bytes` | 이미지 원본 바이트 합 (base64 이전) |
| `prompt` / `candidates` / `total` | `usageMetadata`의 각 토큰 수 |
| `http` / `ok` | HTTP 상태와 판독 성공 여부 |

`image_bytes`를 같이 남기는 이유는 §4.2를 로그에서 바로 대조하기 위해서다.
**바이트가 5배 늘어도 토큰이 그대로면 "토큰은 해상도로 정해진다"가 실데이터로 증명된다.**

### 8.2 설계상 정한 것 세 가지

1. **클라이언트에 넣었다** — `OcrWorker`가 아니다. worker는 최종 결과만 보므로 404 fallback
   재시도의 첫 호출을 놓친다. 클라이언트에 두면 **실제 HTTP 요청 수와 로그 줄 수가 일치**한다.
2. **`usageMetadata`를 `candidates`보다 먼저 파싱한다** — 토큰은 응답이 도착한 시점에 이미
   청구됐다. 응답 형식이 바뀌어 판독에 실패해도 사용량 기록은 남아야 한다.
3. **미측정은 `0`이 아니라 `-1`** — "모델이 0토큰을 청구했다"와 "usageMetadata가 없었다"는
   구분해야 한다. 비-2xx 응답은 토큰이 청구되지 않으므로 아예 로그를 남기지 않는다.

### 8.3 집계 방법

`.env.public`의 `LOG_GEMINI_USAGE=true`로 켜져 있다(끄려면 `false`).
며칠 운영 후 다음으로 집계한다.

```bash
# 이미지 수별 평균 prompt 토큰 — §4.3의 258 / 516 이 맞는지 확인
grep GEMINI_USAGE data/logs/pi-server.log \
  | sed 's/.*images=\([0-9]*\).*prompt=\([0-9-]*\).*/\1 \2/' \
  | awk '$2>=0 {n[$1]++; s[$1]+=$2} END {for (k in n) printf "images=%s  n=%d  avg_prompt=%.1f\n", k, n[k], s[k]/n[k]}'

# 바이트와 토큰의 상관 — 값이 흩어지면 "크기가 아니라 해상도" 명제의 실증
grep GEMINI_USAGE data/logs/pi-server.log \
  | sed 's/.*image_bytes=\([0-9]*\).*prompt=\([0-9-]*\).*/\1 \2/' | sort -n | uniq -c
```

기대값은 `images=1 → prompt ≈ 258 + 프롬프트 텍스트 토큰`, `images=2 → 그보다 258 많음`이다.
실제 값이 다르면 §4의 258/타일 가정을 그 값으로 교체하면 된다.

## 9. 결론

사용자가 짚은 두 근거는 모두 성립하며, 크기가 각각 다음과 같다.

1. **저장 유리** — 이벤트당 **7.52배** (972.6KB → 129.4KB). §7.1 중복 제거 시 **15배**.
2. **토큰 절감** — 요청당 **4배** (1032 → 258 tok). IVA 경로는 아직 2배.

여기에 요청 외 세 가지를 더 들 수 있다.

3. **Pi CPU 22.1배** (270.4ms → 12.2ms) — 옛 비용의 53.5%가 PNG 인코딩이었다.
   옛 코드를 실제로 컴파일해 돌린 값이고, 출력 PNG가 커밋된 실파일과 바이트 단위로 일치한다.
4. **업로드 7.5배** (1296.8KB → 172.5KB base64). 단 다운로드는 불변이다.
5. **OCR 유효 해상도 2.24배** — 토큰을 4배 적게 쓰면서 ROI에는 2.24배 더 배분한다.

가장 설득력 있는 한 줄은 **"811.9KB PNG와 160.7KB JPEG의 토큰이 둘 다 516으로 같았다"**이다.
옛 방식의 병목은 이미지가 컸다는 게 아니라, **큰 대가를 치른 그 이미지가
모델에게 아무 추가 정보도 주지 못했다**는 데 있다.
